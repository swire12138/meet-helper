# 抽象专家知识画像落地方案

## 1. 目标

本方案用于把当前“会议增量直接合并到画像正文”的模式，升级为“抽象专家知识画像系统”。

约束前提：

- 会议记录无法稳定区分发言人。
- 每次会议由用户手动指定一个“抽象专家画像”作为归属对象。
- 一场会议的全部知识与内容，都视为对该专家的一次知识更新。
- 系统必须支持后续长期更新、按来源回溯、整场抽离、错误迁移，避免误选专家后污染长期画像。

目标能力：

- 长期稳定积累专家知识，不再依赖一份越来越长的 Markdown 画像硬拼。
- 每次会议保留全文、摘要、记忆单元与来源关系。
- 问答时按问题动态选择相关知识组，而不是无差别塞入全部历史。
- 允许对某次会议的影响进行整体抽离，或迁移到另一个专家。

## 2. 总体架构

系统分为五层：

1. 原始会议层
2. 会议摘要层
3. 记忆单元层
4. 槽位聚合层
5. 展示与问答层

### 2.1 原始会议层

职责：

- 保存每次会议的完整转写、截图元信息、基础归属信息。
- 这层只保留事实，不做覆盖。

存储内容：

- `transcript.md`
- `meta.json`
- `images.json`
- `summary.json` 之前的原始响应快照（可选）

### 2.2 会议摘要层

职责：

- 为单次会议生成结构化摘要，便于后续检索与回看。
- 作为原始全文与长期画像之间的中间层。

建议字段：

- 本次会议主题
- 本次会议核心结论
- 本次会议新增术语
- 本次会议新增方法/框架
- 本次会议新增风险点
- 本次会议不应进入长期画像的临时内容

### 2.3 记忆单元层

职责：

- 把会议内容拆成标准化“记忆单元”。
- 每条记忆单元都必须带来源会议、证据片段、权重、置信度。
- 这是长期画像的真实数据基础，不再直接由全文或摘要合并画像正文。

### 2.4 槽位聚合层

职责：

- 把记忆单元按类型归入不同槽位。
- 各槽位内部按“加权更新 + 时间衰减 + 候选竞争 + 阈值切换”生成当前主值。

### 2.5 展示与问答层

职责：

- 展示型画像：面向 UI，输出稳定、可读的专家画像。
- 问答型上下文：根据用户问题动态挑选相关槽位、相关会议摘要、相关证据片段。

## 3. 主体模型

系统主体由“用户/参会人”改为“抽象专家画像”。

### 3.1 专家画像

每个专家画像代表一个长期演化的知识容器，例如：

- 糖尿病临床专家
- 房颤诊疗专家
- 医疗运营专家
- AI 产品策略专家

会议更新的不是“某个真实发言人”，而是“这个专家知识体”。

### 3.2 会议归属

每次会议必须手动归属到一个专家：

- 一个会议只归属一个专家。
- 一次会议是对该专家的一次知识注资。
- 如果选错专家，必须支持抽离和迁移。

## 4. 数据组织

建议文件结构如下：

```text
experts/
  {expertSlug}/
    expert.json
    portrait/
      summary.json
      expert.md
    meetings/
      {meetingId}/
        meta.json
        transcript.md
        images.json
        summary.json
        extracted_memories.json
    memory_units/
      units.jsonl
    events/
      ledger.jsonl
    aggregates/
      slots.json
```

各目录职责：

- `expert.json`: 专家基本信息、领域、创建信息、启用状态
- `portrait/summary.json`: 聚合后的结构化画像
- `portrait/expert.md`: 展示给用户的专家画像正文
- `meetings/{meetingId}`: 单次会议完整归档
- `memory_units/units.jsonl`: 该专家所有记忆单元
- `events/ledger.jsonl`: 写入、抽离、迁移等事件账本
- `aggregates/slots.json`: 各槽位当前聚合结果

## 5. 记忆单元设计

### 5.1 单条记忆单元结构

```json
{
  "id": "mem_001",
  "expertSlug": "diabetes-clinical",
  "meetingId": "meeting_20260721_001",
  "slot": "reasoning_frameworks",
  "value": "先评估HbA1c和肾功能，再确定降糖起始方案",
  "valueType": "framework",
  "scope": "mid_term",
  "weight": 5.2,
  "confidence": 0.88,
  "evidence": [
    "糖化血红蛋白已经9.2%，现在先讨论降糖方案和胰岛素起始。",
    "还要结合肾功能评估二甲双胍和SGLT2抑制剂是否适合。"
  ],
  "sourceType": "explicit_statement",
  "status": "active",
  "createdAt": "2026-07-21T15:00:00Z"
}
```

### 5.2 必备属性

- `expertSlug`: 专家归属
- `meetingId`: 来源会议
- `slot`: 归属槽位
- `value`: 记忆内容
- `scope`: 长期 / 中期 / 短期
- `weight`: 本次影响权重
- `confidence`: 抽取置信度
- `evidence`: 证据原文
- `status`: `active / retracted / superseded`

## 6. 槽位设计

建议不再以“人格画像”为中心，而是以“专家知识结构”为中心。

### 6.1 长期稳定槽位

- `core_domain`: 核心领域
- `core_principles`: 核心原则
- `reasoning_frameworks`: 常用判断框架
- `technical_or_clinical_preferences`: 技术/临床偏好
- `terminology_system`: 常用术语体系

### 6.2 中期演化槽位

- `recent_focus_topics`: 最近关注议题
- `recent_decision_patterns`: 最近决策路径
- `recent_solution_patterns`: 最近解决方案模式

### 6.3 短期槽位

- `current_hot_questions`: 当前高频问题
- `temporary_hypotheses`: 阶段性判断
- `meeting_specific_context`: 当前阶段上下文

## 7. 加权更新机制

## 7.1 设计原则

采用“类似稀释股权”的更新直觉，但不是针对整张画像，而是按槽位独立更新。

更新规则：

- 历史内容不能直接失忆。
- 新会议必须可以逐步改变当前画像。
- 越新、越重要、越明确的证据，影响越大。
- 长期稳定槽位更新慢，短期槽位更新快。

## 7.2 会议基础权重

单次会议对某个记忆单元的基础权重 `W` 由以下因子组成：

```text
W = 会议重要度 × 内容长度系数 × 证据明确度 × 抽取置信度 × 槽位缩放系数
```

可选扩展：

- 发言有效度系数
- 重复出现系数
- 决策类内容增强系数

建议初始定义：

- 普通讨论：1.0
- 关键决策会：1.5
- 正式评审 / 专家复盘：2.0

证据明确度建议：

- 明确自述 / 明确结论：1.5
- 多次重复出现：1.2
- 弱推断：0.7

## 7.3 历史衰减

历史有效权重必须做时间衰减，否则画像会逐渐僵死。

```text
effectiveOldWeight = oldWeight × exp(-Δt / τ)
```

不同槽位采用不同 `τ`：

- 长期槽位：120~180 天
- 中期槽位：30~90 天
- 短期槽位：7~30 天

## 7.4 槽位权重上限

每个槽位设置 `historyCap`，防止历史权重无限增长。

示例：

```json
{
  "core_principles": { "historyCap": 120, "tauDays": 180, "switchThreshold": 1.2 },
  "reasoning_frameworks": { "historyCap": 100, "tauDays": 120, "switchThreshold": 1.15 },
  "recent_focus_topics": { "historyCap": 30, "tauDays": 30, "switchThreshold": 1.05 },
  "temporary_hypotheses": { "historyCap": 15, "tauDays": 7, "switchThreshold": 1.0 }
}
```

## 7.5 候选值竞争

槽位内部不是只有一个值，而是维护多个候选值。

示例：

```json
{
  "slot": "reasoning_frameworks",
  "candidateValues": [
    { "value": "先评估HbA1c和肾功能，再定起始方案", "score": 42.6 },
    { "value": "优先按并发症决定方案路径", "score": 17.3 }
  ]
}
```

更新方式：

- 同类新证据：给该候选值加权
- 新候选值：创建新候选并注入初始权重
- 历史候选：先做时间衰减，再参与竞争

## 7.6 主值切换

不建议一条新证据直接改主画像。

切换条件建议满足其一：

- 新候选分数超过当前主候选 `15%~20%`
- 连续 2~3 次会议支持该值
- 新候选总来源权重超过槽位阈值

## 8. 抽离与迁移

## 8.1 必须具备的原因

由于会议是手动归属专家，存在误选专家的风险。

因此系统必须支持：

- 整场会议抽离
- 局部记忆单元抽离
- 挂错专家后的会议迁移

## 8.2 事件账本

每次会议写入必须记录为事件，而不是直接修改最终画像。

事件示例：

```json
{
  "eventId": "evt_001",
  "expertSlug": "diabetes-clinical",
  "meetingId": "meeting_20260721_001",
  "type": "meeting_ingest",
  "memoryUnitIds": ["mem_101", "mem_102"],
  "slotImpacts": [
    { "slot": "recent_focus_topics", "value": "胰岛素起始", "weight": 5.2 }
  ],
  "status": "active",
  "createdAt": "2026-07-21T15:00:00Z"
}
```

状态定义：

- `pending`: 已抽取待确认
- `active`: 已正式入账
- `retracted`: 已抽离
- `moved`: 已迁移到别的专家

## 8.3 抽离方式

### 整场抽离

- 将该会议对应事件标为 `retracted`
- 该会议下的记忆单元全部失效
- 重算槽位聚合
- 重生成画像摘要与展示文档

### 局部抽离

- 对单条记忆单元标记 `retracted`
- 或调整其 `scope`
- 重算聚合

### 迁移

- 从原专家执行 `retract`
- 向目标专家执行 `replay`
- 保留完整来源链路

## 9. 问答检索方案

用户提问时，不直接把所有历史会议塞进上下文。

采用三段式上下文组装：

1. 当前专家的稳定画像
2. 与问题相关的会议摘要组
3. 少量原始证据片段

### 9.1 上下文优先级

- 先取长期稳定槽位主值
- 再取相关中期 / 短期槽位
- 再按主题检索相关会议摘要
- 最后补少量原始证据片段

### 9.2 检索目标

让模型回答时既不失忆，也不被无关旧会议污染。

## 10. UI 与流程变更

需要新增或调整的界面能力：

- 会议开始前，显式选择“本次更新的抽象专家画像”
- 在专家画像页查看：
  - 当前稳定画像
  - 最近新增的会议
  - 会议摘要列表
  - 槽位聚合结果
  - 最近变更历史
- 提供：
  - 整场抽离
  - 单条记忆抽离
  - 迁移到其他专家

## 11. 推荐实施顺序

### 第一阶段：规范存储

- 引入专家目录结构
- 每次会议单独归档全文与摘要
- 不再直接只改画像正文

### 第二阶段：记忆单元与聚合

- 从会议抽取记忆单元
- 建立槽位与加权更新
- 生成结构化画像摘要

### 第三阶段：抽离与迁移

- 建立事件账本
- 支持整场抽离与迁移
- 支持重算聚合

### 第四阶段：问答检索

- 根据用户问题动态组装上下文
- 让专家问答基于相关会议组而不是全文硬塞

## 12. 本方案的边界

本方案当前不包含：

- 向量数据库或复杂召回引擎的强依赖
- 自动识别真实发言人
- 多专家协同融合回答

当前优先确保：

- 存得规范
- 更新可控
- 污染可抽离
- 问答可检索
